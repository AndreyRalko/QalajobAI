# План реализации проекта QalaJob-AI (Фазы 6–16)

Цель: довести проект до production-ready состояния по этапам, указать задачи, зависимости, оценки сроков и критерии приёмки.

## Краткий обзор
Работа разбита по фазам (6–16). Для каждой фазы указаны: задачи, оценки времени, зависимости и критерии готовности.

---

## Общие принципы
- Итеративная работа: доставка минимального рабочего результата для каждой фазы.
- CI/CD и тесты на каждом существенном изменении.
- Рольвая модель: Admin / Employer / Candidate.
- Бэкап данных и миграции версии PostgreSQL при смене схемы.

---

## Фазы и план

### Предварительная подготовка (Setup) — 3 рабочих дня
Задачи:
- Настроить репозиторий, ветвление, CI (GitHub Actions).
- Docker / docker-compose для локального dev (Postgres, Redis, Django).
- Создать шаблон Django-проекта и базовую конфигурацию (env, CORS, logging).
Критерии: проект запускается локально через docker-compose, тест-ран проходит.

### Phase 6 — Application System — 10 рабочих дней
Задачи:
- Модели Application + статусы (Pending, Reviewing, Interview, Accepted, Rejected).
- Эндпойнты: apply, withdraw, list by candidate/employer, history.
- События статусов, аудита, email/push уведомления (черновая реализация).
Критерии: можно подать/отозвать заявку, видна история и статус-уведомления.

### Phase 7 — Admin Panel — 12 рабочих дней
Задачи:
- Dashboard аналитики (основные метрики).
- CRUD управление пользователями, бан/разбан, премиум-менеджмент.
- Модерация вакансий/компаний, просмотр заявок.
- Audit logs и базовые графики.
Критерии: админ может модерать контент и видеть метрики.

### Phase 8 — Subscription System — 7 рабочих дней
Задачи:
- Модели планов (Free, Premium, Business), ограничения фич.
- Badge, срок действия, история подписок, апгрейд-процесс.
Критерии: пользователь может купить план (симуляция), badge видна, истечение срока обрабатывается.

### Phase 9 — Payment Architecture — 10 рабочих дней
Задачи:
- Интеграция платёжных провайдеров: Stripe (основной), Kaspi/Halyk — адаптеры.
- Payment records, invoices, webhook обработчики, статус-трекинг.
Критерии: успешная запись платежа через Stripe + вебхуки, выставление счета.

### Phase 10 — AI Features — 14 рабочих дней (R&D + MVP)
Задачи:
- AI Vacancy Matching, Resume Analysis, Cover Letter Gen, Interview Prep.
- Сервисная обёртка (ai/services.py) + асинхронные задачи (Celery/RQ).
Критерии: базовый matching и генерация доступны через API; метрики качества.

### Phase 11 — Django Backend Architecture — 20–30 рабочих дней
Задачи:
- Создать приложения: users, profiles, companies, vacancies, applications, subscriptions, resumes, saved_jobs, ai, admin_api.
- Для каждого: models.py, serializers.py, views.py, urls.py, permissions.py, admin.py, services.py.
- JWT + Firebase интеграция, Swagger (drf-spectacular), тесты.
Критерии: полнофункциональный API, покрытие ключевых эндпойнтов тестами.

### Phase 12 — Database Review (Firestore -> Postgres) — 6 дней
Задачи:
- Анализ текущих коллекций Firestore (если используются), оптимизация схемы, правила безопасности, индексы.
- Миграции данных (при необходимости).
Критерии: схема оптимизирована, правила безопасности и индексы описаны.

### Phase 13 — Security — 8 рабочих дней
Задачи:
- RBAC: Student/Employer/Admin.
- Rate limiting, input validation, XSS/CSRF защита, firewall правил.
- Firestore security rules (если применимо).
Критерии: базовый security-audit пройден, уязвимости устранены.

### Phase 14 — Performance — 8 рабочих дней
Задачи:
- Профилирование медленных запросов, оптимизация индексами.
- Оптимизация фронтенда (re-renders, bundle).
Критерии: метрики времени отклика в пределах SLA; уменьшение крупного бандла.

### Phase 15 — Deployment — 5 рабочих дней
Задачи:
- Настройка production окружения (Docker, env), Vercel/Heroku/Cloud.
- Конфигурация переменных, SSL, мониторинг.
Критерии: успешный production deploy, smoke тесты зелёные.

### Phase 16 — Final Report — 4 рабочих дней
Задачи:
- Сгенерировать отчёты: архитектура, безопасность, производительность, БД, мульти-язык, readiness scores.
- Завершить документированную чек-лист-листу.
Критерии: отчёт готов и утверждён.

---

## Риски и зависимости
- Интеграции платёжных провайдеров требуют тестовых аккаунтов.
- AI-фичи зависят от качества данных и внешних моделей.
- Если Firestore активно используется, миграции в Postgres увеличат сложность.

---

## Принятые метрики успеха
- API: 95% успешных запросов < 300ms (для ключевых эндпойнтов).
- Тестовое покрытие: минимум 70% для backend бизнес-логики.
- Безопасность: нет критических уязвимостей по автоматическим сканерам.
